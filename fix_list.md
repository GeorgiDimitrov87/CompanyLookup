
1. Crash in the directory-fallback path (highest impact). company_discovery Tier 2 calls resolve_company(db, job, name, None, ...) and resolve_company immediately does is_social_media_domain(domain) → domain.lower() on None. I confirmed this raises AttributeError. So the whole "no official site found, fall back to a directory listing" branch — which has a 12-line comment block explaining its design — never works. Worse, _run_stage swallows it, writes an "Uncertain/Low" result, and the chain keeps going, so the job finishes as COMPLETE with everything "Not found" instead of surfacing the error. Fix: guard for None in is_social_media_domain.
2. Meta Ads card always shows zero. StageCardsStream.tsx renders data.active_ads_count and data.reason, but meta_ads.py writes ads, note, and check_timestamp. Found ads never display.
3. "Overall Confidence" in the report is not the overall confidence. aggregator.run computes compute_overall_confidence(...) and builds a report dict, then returns it into the void — nothing is persisted, no column exists for it. The report page instead displays stages.company_discovery.confidence labeled "Overall Confidence". So the one number an executive reader would trust most is the wrong number.
4. Double-counted website signals. In website_verification, dsim > 0.4 grants domain_similarity (+40) and title_match (+25), and clean_domain in body/meta grants two more. One underlying signal inflates up to four scores, so any reachable site with a matching domain lands at ~90 → "Verified" without the title ever being checked. The stage is closer to "is the domain live and does it look like the name" than multi-factor verification.
5. docker-compose.prod.yml is decorative. No ports published, no reverse proxy service, no migration step, and the frontend gets NEXT_PUBLIC_API_URL=https://${DOMAIN_NAME}/api while api.ts appends /api/lookups → requests go to /api/api/lookups. NEXT_PUBLIC_WS_URL isn't set at all, so prod falls back to ws://localhost:8000 and live updates are dead. It also builds the same Dockerfile, which runs npm run dev — the Next dev server in production. output: "standalone" in next.config.ts is configured but unused. Postgres is 15 here vs 16 in dev.
6. _run_stage never rolls back. On exception it immediately calls save_stage_result on the same session. If the failure came from a flush/commit, that write fails too and the error is lost entirely.
7. Phone extraction is near-useless. [\+]?[\d\s\-\(\)]{7,15} matches years, prices, IDs, any long digit run. Then both website_verification and contact_enrichment filter results through a hardcoded Indian mobile regex — an odd, undocumented geographic assumption for a general product, and it discards legitimate company mobile numbers.

Overclaiming in the docs
Tech_arch.md says stages run "in parallel" as "8 isolated worker sub-tasks." They don't — celery_tasks.py is a strictly serial chain, each task queuing the next. --concurrency=4 gives you concurrent jobs, never a faster single lookup.

It also claims Jaro-Winkler and Levenshtein; the code uses difflib.SequenceMatcher (Ratcliff/Obershelp). It claims Proxycurl enrichment and a linkedin_provider abstraction — both files exist, return None, and are imported by nothing. It describes confidence bands as 80/50 while scoring.py uses 75/45. And it lists a "Tier 3 web snippet fallback" for contacts that isn't in contact_enrichment.py. README says cd CompanyLookup (wrong folder) and numbers nine items under an "8-Stage" heading.

None of these are fatal, but if this was submitted as a technical explainer, a reviewer who reads the code will notice, and that costs more credibility than the bugs do.

Security notes
No auth anywhere: API, WebSocket, and Flower on 5555 are all open. allow_origins=["*"] with allow_credentials=True is an invalid CORS combination that browsers reject outright. No rate limiting on POST /lookups, and each job fans out into dozens of outbound requests. fetch_page follows redirects to arbitrary URLs sourced from search results with no private-IP/metadata-endpoint blocking, which is a textbook SSRF surface for a crawler. Acceptable for a local demo, worth naming explicitly as known gaps.

Also: no robots.txt handling and a bot UA with no contact address, which matters for a product whose whole premise is crawling third-party sites.
